# Manufacturing ERP data audit

This project profiles manufacturing ERP CSV exports, identifies product duplicate candidates, and reconciles deliveries against invoices. It produces review evidence for data cleanup and billing investigation. The supplied data is in `data/` and source files are preserved.

## Setup and execution

Use Python 3.9 or later and the pinned packages in `requirements.txt`. From the project root:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt

python 00_explore_data.py
python 01_product_dedup.py
python 02_billing_reconciliation.py
python 02_reconcile_billing.py
python -m pytest -q
```

The profiling script prints its findings, including inventory quantity variances, to the terminal. The other scripts write CSV reports to `reports/`. The product script accepts `--reference-threshold` and `--name-threshold` options. The `02_reconcile_billing.py` script also accepts `--data-dir` and `--output-dir`.

## Input schemas

The input files are CSVs with these column names:

| File | Columns |
| --- | --- |
| `products.csv` | `product_id`, `internal_ref`, `name`, `uom`, `category`, `active` |
| `sales_orders.csv` | `so`, `customer`, `internal_ref`, `qty_ordered`, `unit_price`, `order_date`, `due_date` |
| `deliveries.csv` | `delivery`, `so`, `internal_ref`, `qty_shipped`, `ship_date`, `state` |
| `invoices.csv` | `invoice`, `so`, `internal_ref`, `qty_invoiced`, `unit_price`, `invoice_date`, `state` |
| `inventory_counts.csv` | `lot`, `internal_ref`, `location`, `uom`, `system_qty`, `counted_qty` |

The profiler expects these exact schemas, ISO dates, integer quantities, decimal prices and `True`/`False` active values. Billing scripts accept the required columns plus extra columns and use nonnegative decimal quantities and prices. Recognized delivery states are `done` and `cancelled`; invoice states are `posted` and `draft`.

## Reports

- `product_duplicates.csv` contains candidate pairs, proposed keeper, matching evidence, confidence and unit conflicts.
- `order_reconciliation.csv` and `billing_issues.csv`, produced by `02_billing_reconciliation.py`, provide order-key balances and issue details. They distinguish ordinary, review and unquantified results.
- `billing_reconciliation.csv`, `billing_exceptions.csv` and `billing_duplicate_candidates.csv`, produced by `02_reconcile_billing.py`, provide balances, invalid or unmatched records, and suspected duplicate transaction records.
- `manager_note.md` is a written snapshot of findings. It is not regenerated by the scripts.

The billing scripts use different key handling. The first trims order keys, uppercases references, and combines repeated order rows when customer and price agree. The second uses exact keys and excludes repeated order keys as ambiguous. The first retains invalid order keys as unquantified rows; the second excludes affected keys from its balances and reports exceptions. Review the appropriate exception or issue report alongside either set of balances.

## Method and assumptions

Product matching trims and uppercases references and normalizes decimal formatting for coil widths. It parses available family, dimensions, wall, length, cut status, grade and gauge information from references and descriptions. Equal nonempty normalized references produce candidates, including conflicting pairs flagged for review. Other candidates require matching category and compatible specification evidence; RapidFuzz reference and name scores help label matches. The proposed keeper favors active, complete and internally consistent records.

Similarity does not establish product equivalence. Specifications can be incomplete or disagree, gauge-to-thickness equivalence needs verification, and units of measure can conflict. Candidates are never automatically merged.

Billing assumes a common currency and comparable units, with completed deliveries billed at the order unit price. Deliveries and invoices are aggregated independently by sales order and product before comparison. A direct join of multiple deliveries to multiple invoices would multiply rows and inflate quantities and values. Only `done` deliveries and `posted` invoices enter the financial comparison. Cancelled deliveries and draft invoices are displayed separately because they do not represent completed shipments or posted billing. Suspected duplicate transactions remain in the totals pending review.

For each valid order key, with `D` as completed delivery quantity, `Q` as posted invoice quantity and `P` as order price:

```text
expected value  = D × P
posted value    = sum(invoice quantity × invoice unit price)
quantity impact = (Q − D) × P
price impact    = sum(invoice quantity × (invoice unit price − P))
billing gap     = posted value − expected value = quantity impact + price impact
```

The second reconciliation report calls these impacts and gap `quantity_variance`, `price_variance` and `billing_variance`. Negative gaps indicate potential shortfalls and positive gaps indicate potential excesses. Quantity and price impacts are components of the gap and should not be added to it again.

Inventory quantity variance is counted quantity minus system quantity at the same cutoff. The export contains no inventory unit cost or valuation data, so a financial inventory variance cannot be calculated.

## Limitations and references

Results are review leads, not confirmed losses or proof of duplicate records. The exports do not establish shipment authorization, discounts, credit notes, taxes, currency, payments or the accuracy of physical counts. Parsing relies on the supplied product naming and reference conventions. Review source documents and exceptions before corrective action.

The tests cover synthetic edge cases and supplied CSVs, including product matching, state separation, duplicate candidates, prices, aggregation, missing columns and empty inputs.
